## Open questions
- DES-10 / DES-14 policy: fmrimod refits orthogonal bases on a subset and keeps zero columns for excluded levels. Both are defensible Python choices, but they diverge from R numerics and design shape. The steward should rule port-or-caveat in one S2 note, together with the v1 zero-event row.
- DES-01 reach: `contrast_weights(EventModel)` is in `fmrimod.__all__`, but the typed fit path (`condition()`/`OmnibusContrast`) is the recommended one, and `FmriModel.contrast_weights()` returns `{}` for an `EventModel` (`fmrimod/model/fmri_model.py:189-202`), so `fit.contrast("name")` never sees attached contrasts. Port the embedding, or retire term-attached contrasts in favour of typed ones? Either way the silent drop of spec `contrasts=` should become an error.
- Fit-level `ContrastSpec` resolution (`fmrimod/glm/fmri_lm.py:770` with `_FitColumnTerm`) matches `Formula("A")` but not `Formula("cond == 'A'")` against realized names like `cond_cond.A` (zero weights plus a warning). Pre-existing, not drift.
- Cross-audit lead (fmrireg fit-core auditor), a multi-variable `hrf(Time, Cond)` that drops `Cond`: confirmed and recorded as DES-06. **Pre-existing, not drift.** The fmrimod string parser reads only `ft.arguments[0]` (`fmrimod/formula/parser.py:468-475`). R has crossed every `...` variable of `hrf()` since before the pin; in range, only the design-side handling of multi-variable terms changed (`d37175b`, `b718336`, `f63135b`; covered by DES-27 and DES-11). The spec path (`fmrimod/spec/builders.py:47`, `*variables`) and the `a:b` string form are unaffected.
- Cross-audit lead (fmridataset auditor) on numbering runs by first appearance: **pre-existing, not drift.** fmrimod `_parse_block_ids` (`fmrimod/design/event_model.py:2473-2481`) numbers block labels by first appearance, so run labels `[1, 3]` become blockids `[1, 2]` and run 3's events are convolved into run 2's window with no warning (`fmridesign_blockids.py`: runs with signal `[True, True, False]`). R `canonicalize_blockids()` does the same (`R/event_model_helpers.R:60-73`, `match(x, unique(x))`); the only change in range is the refactor `70531ba`. So fmrimod matches R here, but both are hazardous when a run has no events. The one R/fmrimod difference, also pre-existing at the pin: R rejects decreasing block ids (`'blockids' must be non-decreasing`), while fmrimod accepts `[2, 1, 2]` and maps it to `[1, 2, 1]`.
- Ordering of interaction cells: R lists the first factor fastest (`a.p_b.x, a.q_b.x, ...`, `test-design-names.R:248`); fmrimod lists it slowest (`cond.A_task.x, cond.A_task.y, ...`). fmrimod is consistent with itself (Fcontrasts and Kronecker order agree), but positional parity tests against R need to reorder. Pre-existing.
- Factor x modulator design columns are named `cond_rt_cond:rt_1` (`fmrimod/design/event_model.py:1868-1869`, via `get_column_names()`), while the term-level conditions are `cond.A_rt`, and R names them `cond_rt_cond.A_rt`. Combined with DES-12, pattern contrasts on modulator terms cannot target levels by name. Pre-existing.
- Interaction-term modulators are mean-centred by default (`hrf(cond:rt)`; per-event amplitudes `[-1.125, ...]`), and R does not centre them. This is documented for `spec.hrf(modulators=, center_modulators=)` (`fmrimod/spec/builders.py:72-80`), but it is not clear that the same default is intended for the `:` interaction path.
