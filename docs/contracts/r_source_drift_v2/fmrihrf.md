# R-source drift v2: fmrihrf 0.4.0.9000 (`69be541`..`5b63d6a`)

Part of [`r_source_drift_inventory_v2.md`](../r_source_drift_inventory_v2.md). The classes, method and wave plan are defined there. `repro/` scripts run against fmrimod HEAD `4f14a19` with `.venv/bin/python`.

Range: 82 non-merge commits, 25 R/src files changed (fmrimod HEAD `4f14a19`). Note that the v1 pin sat *inside* 0.4.0 development: the 0.4.0 that went to CRAN (prepared in `50c9b1e`, 2026-10-03) already contains the SPMG, block, B-spline and weighted-HRF changes below, so "fmrihrf 0.4.0" no longer means what it meant at v1.

Refactor-only work: the `hrf-reg` / `hrf-core` / `hrf-cli-plot` simplification series (`3d050ed`, `df398ec`, `784b768`, `f8220f0`, `d640a6b`, `ba97f77`, `6fc5e5e`, `2e5b6f0`, `5b8e453`, `472b9fe`, `b95e73b`, `7ea8d56`, `c69a367`, `4cce9d3`, `3644656`, `2d97b49`, `0e3d715`, `d3ee6d2`, `0fa1949`, `01c632b`). These share the decorator pipeline between `gen_hrf`/`getHRF`, add `.as_closed_hrf` metadata capture, merge duplicate `deriv`/`penalty_matrix` branches, remove dead helpers (`hrf_ident`, `makeDeriv`, the old `.hrf_half_cosine`, `neural_input_rcpp`) and tidy roxygen. Also refactor-only: the Rcpp exception plumbing (#42, `50c9b1e`), OpenMP removal and computing only the conv samples the grid needs (`acba033`, `4512064`, perf only, results within 1.3e-15), FIR vectorisation, the `cachem` load-time cache (`1fbb610`), and CRAN/R-hub/manual/vignette/CI housekeeping (`1b629fa`, `2ab2b60`, `6edcd1c`, `272a0e6`, `4e8ccb6`, `facbf14`, `fb55b2d`, `4811238`, `0d56a41`, `b9f6a90`, `39f5c83`, `e89ecc3`, `40c2125`, `6c51afc`). Docs-only: `bb06202`, `a71d64e`, `6334b08` (documentation that goes with HRF-10), and the `summate`/`normalize` wording for boxcar and weighted HRFs. None of these get rows.

## Open questions
- SPMG2 column 2 (pre-existing, not drift, but it is the last SPMG divergence from R HEAD). fmrimod uses a finite difference in the *delay* parameter (`hrf/derivatives.py:263-294`). Its correlation with Nilearn's `spm_time_derivative` is only 0.9647 on Nilearn's grid (`repro/fmrihrf_extra.py`). R's analytic dh/dt correlates 0.9995 with an onset-shift difference, which is what Nilearn and SPM `spm_get_bf` actually perturb. The comment in `benchmarks/parity/tier_a_spm_derivative_basis/workflow.py:284-290` says fmrimod uses closed-form `spmg1_derivative`, which is stale. Should column 2 become an onset-shift difference (Nilearn) or analytic dh/dt (R)? Either would let the `allow_rescale`/Pearson-0.95 gate tighten.
- SPMG undershoot ratio: Nilearn uses 0.167, SPM `p(5)=6` and R HEAD use exactly 1/6. Should fmrimod keep 0.167, which leaves a permanent 2e-4 relative gap to R? Separately, should `HRF_SPMG1.span` stay at 32 (Nilearn) when R uses 24, a 1.2% regressor gap?
- The AGENTS.md note "Twenty-two cross_testing failures against fmrihrf 0.4.0 (×10)" describes the pre-release 0.4.0 at the v1 pin. CRAN 0.4.0 contains `daca7ba`. This is unverified here (no R installed), but re-baselining after installing CRAN 0.4.0 should turn those into ratio/span/derivative-column failures or passes.
- HRF-10 is a semantics decision. Upstream deliberately made `neural_input` the conv density, which reverses the premise of the fmrimod docstring. If fmrimod prefers to keep a plotting-oriented boxcar, the `linspace` step bug and the vanishing sub-resolution blocks still need fixing, and the docstring should say it no longer matches R.
- The `*_Legacy` SPMG classes now reproduce no released R version (R moved to A1 = 1/120 before CRAN 0.4.0). Retire them, or relabel them "pre-0.4.0 fmrihrf parameterization"? Fixing HRF-08 on a retirement candidate may not be worth it.
- HRF-17 shape: is a plain `Regressor` enough for `feature_regressor`, or does fmrimod want a frozen subclass that carries `dt`/`center`/`scale`/`mask` metadata, as R's `FeatureReg` does? Its `shift()` refuses negative times and does not re-center.
