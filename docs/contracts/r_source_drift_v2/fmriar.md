# R-source drift v2: fmriAR 0.4.2 (`c7f370a`..`bb0789c`)

Part of [`r_source_drift_inventory_v2.md`](../r_source_drift_inventory_v2.md). The classes, method and wave plan are defined there. `repro/` scripts run against fmrimod HEAD `4f14a19` with `.venv/bin/python`.

Range: 9 non-merge commits, 19 R/src files changed (13 R, 6 src). Behaviour lives in five commits: `ca27f27` (0.3.3 design-residual check), `617bd87` (0.4.0 bulk: exact start-up, pooled ARMA, BIC penalty, censor/plan fixes, HAC), `a75a5de` (ARMA order selection), `5f5fc32` + `bd4e03f` (0.4.1: voxel-pooled parcels, stable bias correction, AFNI `vrt`), `61b89ff` (0.4.2: design-effect BIC for AR). The rest is refactor-only. The R segment lag-sum loop and the Hannan-Rissanen normal equations moved to C++ (`pooled_acvf_seg_cpp`, `hr_normal_eq_cpp`), with identical results; the tests compare them against plain-R references. OpenMP is actually compiled now and honours `fmriAR.max_threads`, and R API calls were moved out of the parallel region. The `arma_whiten_inplace(exact_first_ar1=)` argument was renamed `exact_first`. `acvf_bias_matrix()` became low-rank, O(L²·n·r) instead of O(L²·n²), identical to 1e-12; fmrimod's `acvf.py:326-367` is still the dense form, which is a possible perf follow-up but not a behaviour change. HC0 is vectorised (identical). Parcel whitening caches one whitened X per distinct filter (identical values). The print label changed (see AR-02). Also housekeeping: roxygen/man, README and vignette rewrites, NEWS, cran-comments, a win-builder workflow, .Rbuildignore/.gitignore, and DESCRIPTION 0.3.3 → 0.4.2. `tools/validation/accuracy_benchmark.R` is a seeded harness that runs the same scenarios against two installed versions; it is R tooling, but a ready template for a fmrimod accuracy benchmark.

The headline is that four of the formulas wave1 just ported were themselves corrected upstream: the BIC (AR-01), the bias-correction solve (AR-05), the parcel estimation basis (AR-04) and global run pooling (AR-12). In addition, `acorr_diagnostics`, which v1 marked `done`, has drifted (AR-09), and the wave1 ARMA-censoring warning is now stale (AR-03).

## Red checks (wrong-result and contract rows)

Scripts are in [`repro/`](repro/). They share R transcriptions in `fmriar_common.py`.

- **AR-01.** Red check: in `tests/test_ar/test_estimator_correctness.py`, (a) 300 seeded single-voxel AR(1) series, n=200: `mean(order > 1) < 0.08`; (b) 20 seeds of 30 voxels × 300 frames AR(2) (0.5, −0.1): `order == 2` in ≥ 90%; (c) `_bic_n` on 40 identical columns returns n_frames. All are red at HEAD. Cheap pass disqualified: fixing only `2n → n` passes (a) but under-selects in (b), because frames-only N is the 0.4.1 bug. ## Open questions

- AR-05 brings in two heuristics as-is: `sv_tol = 0.1` relative to the median singular value and a 25% zero-tail. Port them verbatim as parity constants, or expose them? I recommend verbatim private constants.
- Cross-package: R `fmrireg` (`R/fmriAR_adapter.R`, `R/fmri_lm_ar_integration.R`) and `fmrilss` call `fmriAR::fit_noise` / `whiten_apply`, so AR-01, AR-02 and AR-12 change R `fmri_lm` and LSS results. fmrimod's `fmri_lm` AR path (`fmrimod/ar/integration.py:25-144`, `estimate_ar` + `ar_whiten_matrix`) bypasses `fit_noise` entirely, while `fmrimod/single/_prewhiten.py:311-335` uses it. The fmrireg auditor should decide whether `fmri_lm` should route through `fit_noise` to inherit these fixes.
- `fmrimod/ar/integration.py:269` (`iterative_ar_gls` parcel path) needs per-run censor regardless of AR-16. R's `n_time` guard would merely drop the foreign censor set, not supply the right one.
- `fmrimod/single/_prewhiten.py:303-322` computes residuals from an intercept-augmented design but passes `design=config.design` to `fit_noise`. The AR-14 orthogonality check passes for nested designs, yet the correction is derived for a different operator than the one that formed the residuals. Is this intended?
- Wave1 nits, not upstream drift: `apply_acvf_correction` / `drop_unusable_corrections` use a 2-norm `1/cond` (`fmrimod/ar/acvf.py:254, :427`), while R uses `rcond()` (1-norm estimate), so the 1e-6 threshold differs slightly. `hr_arma`'s `step1="burg"` is accepted but ignored (`fmrimod/ar/hr_arma.py:132-143` always uses Yule-Walker).
- AR-23 and AR-26 are additive kwargs on top-level functions. I tagged them S2 because they change stable signatures, but the steward may downgrade them. AR-27 (`WhitenResult.censor`) and AR-16 (`WhiteningPlan.n_time`) are additive fields on `fmrimod.ar` classes that are not in `fmrimod.__all__`, so I did not tag them S2.
