# R-source drift v2: fmrireg 0.3.0.9000: first-level fit core (`063c8ef`..`0321e77`)

Part of [`r_source_drift_inventory_v2.md`](../r_source_drift_inventory_v2.md). The classes, method and wave plan are defined there. `repro/` scripts run against fmrimod HEAD `4f14a19` with `.venv/bin/python`.

Range: 166 non-merge commits and 92 R/src files for the whole package; 84 of those commits and 50 of those files are in this auditor's scope (fit core, AR adapter, robust, sketch/low-rank, contrasts evaluation, betas, simulate, HRF estimation helpers). Evidence scripts live in [`repro/`](repro/) (the shared two-run fixture is `repro/fmrireg_a_fixture.py`). All script output quoted here comes from fmrimod HEAD `4f14a19` run under `.venv`.

Refactor-only work (no rows): the two simplification phases (`e9e724a`, `832fa39`, `aaa109f`, `1593eb3`, `e612797`, `d16d6d6`, `73ce98f`, `0b20cd7`, `bd5b5d6`, `6565fb6`, `846ab4f`, `ff1bf76`, `67f90b2`, `b30227b`, `fd62271`, `2c17705`, `1954d9e`, `060616a`, `b8138c5`, `c159ecf`, `4722e2d`, `1016dba` merge part) fold the legacy AR compat layer into the fmriAR adapter, merge the duplicate `fmri_lm` front-ends, consolidate `create_fmri_model` (three definitions → one, same behaviour), and delete about 3,000 lines of unreachable code. That includes `fmri_lm_bootstrap.R`, `bootstrap.R`, `fmri_lm_contrasts.R`, `fmri_lm_effective_df.R`, `compat-legacy-ar-impl.R`, `fmri_lm_runwise_integrated.R`, `sandwich_variance_doc.R`, `lss_fast`, `multiresponse_rlm`, `fast_rlm_run` and `src/inst_correlation.cpp`. The commits say all of these were unreachable from exports, so this is consolidation, not a feature retraction (see REG-A-28). The range also has migration to the `fmridataset` frame API (`f5f6dd9`, `fcc9888`, `26d01e4`, `1824c35`; `matrix_dataset`→`matrix_frame` etc.), re-exported fmridesign generics (`616e6d5`), and print/plot/cli overhauls (`4c099df`, `0f115a5`, `3a3ead4`, `6a0b2f4`, `ba58f1a`). Plumbing work: `exact=TRUE` `$` matching (`f189d91`), one thread helper / RcppParallel and furrr dropped / `future.apply` everywhere (`1862702`, `27d1543`), generated SRHT wrappers (`62589e0`), SRHT kernel speed-up with bit-identical output (`061d3e1`, `8c3a8e8`). Pure performance items from the review plan, each with an equivalence test: P-D1 lazy `Pinv`, P-D2 lazy chunks, P-D3 HAC hoisting, `9409898` one `(X'X)^-1` per model, P-C1/P-C2, P-E1. Also out of scope here: CI, codemeta, pins, coverage-only test files (`a3cf17e`), mote chores, and the plan documents (`471e872`, `7dddd96`, `9d7fb01`, `206600c`, `5922a3a`, `dbb5a6e`).

## Open questions

- These are fmrimod bugs that the R spec now exposes rather than R drift in the narrow sense: REG-A-01/02/03/04/06/12/13. Several predate the v1 pin; v1 did not inventory the AR/robust fit core at this depth. The in-range R tests (`test-review-D-*`, `test-fmri-lm-voxelwise-noise-contract.R`, `test-ar-estimator-contracts.R`) are the natural red checks. Should they share one epic with a "fit-core composition" bead rather than separate drift beads? The common root of REG-A-01/02/04/16 is that `iterative_gls` and `robust_refit` re-read raw data instead of composing on the engine's preprocessed run matrices.
- REG-A-03 uses fmrimod's own wave-1 `fit_noise(design=)` port as the R oracle. Its correctness rests on v1's `tests/test_ar/test_estimator_correctness.py`. R is not installed here, so it was not cross-checked against fmriAR itself.
- Pre-existing divergences, not drift, flagged for the steward:
  - The default baseline. R `create_fmri_model()` (consolidated in `832fa39`, behaviour unchanged) uses `baseline_model(basis = "bs", degree = max(ceiling(median(run_len)/100), 3))`. fmrimod defaults to a constant runwise intercept (`spec/_compile.py:354-359`, `glm/fmri_lm.py:1497-1499`), so default fits differ numerically.
  - The joint-scope AR/robust/HAC/sandwich/Satterthwaite `variance_spec` paths have no fmrimod counterpart.
- Outside this scope (fmridesign lineage), seen while checking REG-A-09: `fmri_lm("hrf(Time, Cond)", ds)` silently builds only the `Time` columns. `hrf(Time:Cond)` / `hrf(Time*Cond)` give crossed columns with the *last* factor varying fastest; fmridesign varies the first factor fastest (`test-review-C-gen-contrast.R` block 4). Worth handing to the fmridesign auditor.
- REG-A-07: R sets t = 0, p = 1 when se == 0 even for a nonzero estimate. fmrimod's `contrast_t` returns NaN there. Which convention should the single helper adopt? NaN is arguably more honest, but `FmriLm.tstat()` and `contrast_t` must at least agree.
- Not checked: whether `fmri_latent_lm` with `robust` is refused, as R E2 (`bc56286`) now requires; this needs a `LatentDataset` fixture. Also not checked: whether fmrimod's crossed/subsetted HRF contrast weights match R's `test_subset_contrast_offset_weights.R` oracle (`2fe1498`).
- A nit outside the drift question: `fmrimod.glm.fmri_rlm` forces `robust.type="huber"` even when the caller's config asks for bisquare (`glm/compat.py:497`).
